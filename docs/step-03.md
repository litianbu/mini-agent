# 第三步：工具循环 —— 让 agent 真的能做事

前两步模型只会"说"。这一步起，它能"做"。

## 核心就一个 while

```
调用模型 → 它说要调工具？→ 执行 → 结果塞回对话 → 再调用
        → 它不调了？→ 结束
```

这就是 ReAct（Reason + Act）的全部。市面上所有 agent 框架，
剥开封装后跑的都是这个循环。文件在 `app/agent/loop.py`，
真正的逻辑不到 40 行。

## 三个坑，全在这一个循环里

**① 工具调用是分多帧传来的**

模型不会一次给你完整的 `read_file({"path":"app/main.py"})`，而是：

```
帧1: {"index":0,"id":"call_abc","function":{"name":"read_file","arguments":""}}
帧2: {"index":0,"function":{"arguments":"{\"path\":"}}
帧3: {"index":0,"function":{"arguments":"\"app/main.py\"}"}}
```

`id` 和 `name` 通常只在第一帧出现，`arguments` 要**字符串拼接**。
拼错的表现是参数变成残废 JSON——而且只在真模型上才暴露，
假模型测不出来。见 `delta.py` 的 `ToolCallDelta` 和 `loop.py` 的 `_Accumulator`。

**② tool_call_id 必须配对**

结果回传时带上 `tool_call_id`，模型才知道这份结果属于哪次调用。
配对错了，模型会拿错结果继续推理——错得很隐蔽，不报错，只是答得离谱。

**③ 必须刹车**

模型可能一直调工具，永不收尾。`MAX_ROUNDS = 8`，
跑满就发一个错误事件强制停止。没有这一行，你的账户可能一夜清零。

## 四个工具

| 工具 | 作用 | 安全措施 |
|---|---|---|
| `read_file` | 读文件（带行号） | 路径必须在仓库内 |
| `write_file` | 写文件 | 同上 |
| `glob` | 按模式找文件 | 排除 node_modules/.venv |
| `bash` | 跑命令 | 固定工作目录 + 30s 超时 + 危险命令黑名单 |

**路径校验为什么必须有**：模型是"外部输入"。它可能因为幻觉写出
`../../etc/passwd`——不是恶意，但一样会把机器搞坏。
`_safe_path()` 用 `resolve()` 展开 `..` 后检查是否在仓库内。

## 验证

```bash
cd apps/backend
uv run mini-agent "读一下 app/agent/delta.py 的前 5 行"
```

应该看到 `⚙ read_file(...)` 然后是 `✓` 加模型基于真实内容的回答。

界面上也有了「工具调用」卡片：蓝点=进行中，绿点=成功，红点=失败。

## 系统提示词：agent 的"工作手册"

没有提示词时实测：问"数一下 app/agent/tools 下的文件"，
模型把 `app/agent/tools` 当成仓库根下的路径，试了不存在，
用 `bash find` 满仓库找，绕了 **6 轮 11.5 秒**才得到答案。

加上 `app/agent/prompt.py` 后（写清工作区根目录 + 路径基准 + 工具用法）：

```
同一问题 → 2 轮，3.3 秒
```

聊天机器人只需要"人设"，**agent 还需要"工作手册"**：
你在哪、路径怎么算、哪些工具该用在什么场景。
这段文字直接决定 agent 干活靠不靠谱，值得反复调。

## 一件值得注意的事

`loop.py` 从 84 行长到 193 行，但**调用方一行没改**——`api/routes/chat.py`、
`cli.py`、前端全都不动，只是自动开始收到两种新事件。

这就是 S1 先定事件契约的价值：加能力时，只改核心。
