# 第十步：文档切分（RAG 的第一步）

S12-1。RAG 的完整链路是五步，这一步只做**第一步**：

```
文档 → ① 切分 → ② 向量化 → ③ 存库 → ④ 检索 → ⑤ 拼进 prompt
       ↑ 只做这个
```

后面四步都要联网、要 key、要数据库。只有切分是纯本地的——
**所以它可以在没有 embedding key 的情况下先做完。**

## RAG 是什么，为什么需要它

大模型有两个硬限制，RAG 就是绕开它们的办法。

**限制一：它不知道你的私有文档。**

你问「这个项目的上下文裁剪是怎么做的」，模型只能编——
它训练时没见过你的仓库。把整篇文档塞进 prompt 是一种办法，
但撞上限制二。

**限制二：上下文窗口有限，而且很贵。**

13 篇文档约 6 万字。每次都全塞进去：

| 做法 | 每次输入 | 问题 |
|---|---|---|
| 全塞 | ≈ 35000 token | 贵、慢、无关内容干扰判断 |
| 检索后塞 | ≈ 1500 token | 只塞最相关的几片 |

**RAG（Retrieval-Augmented Generation）= 先查资料，再回答。**

```
用户问题
  → ① 把问题也变成向量
  → ② 在库里找最像的几片文档（向量相似）
  → ③ 把这几片 + 原问题一起发给模型
  → ④ 模型基于这几片回答
```

「最像」不是关键词匹配，是**语义相似**：「怎么报销」和「差旅费用申报流程」
字面上没有一个词相同，向量却很近。这是下一步（S12-2）要看的现象。

## 为什么切分值得单独一步做

因为**检索的最小单位就是一个片段**。

检索不会返回「整篇 step-07.md」，只会返回「第 1 片、第 3 片」。
所以切得好不好，直接决定检索能不能用：

```
切得好的片段：      问「为什么要裁剪上下文」
                    命中「第七步 > 要解决的是什么」← 正好是答案

切得差的片段：      从半句话中间开始，前面是上一段的结尾
                    命中了也读不懂
```

**RAG 的效果八成在切分和检索，不在模型。** 后面 embedding 再准，
也救不回一个从代码块中间劈开的片段。

## 一个片段该多大

这是切分里唯一需要拍板的数字，两个方向都有代价。

| 片段大小 | 好处 | 代价 |
|---|---|---|
| 太大（2000+ 字） | 上下文完整 | 噪声多，相似度被稀释，检索不准 |
| 太小（100 字） | 精准 | 语义不完整，回答缺前因后果 |

取 **600 字符**，依据是模型的实际限制：

```
bge-m3 单次输入上限 = 7500 字节
中文 UTF-8 一个字 3 字节 → 约 2500 个中文字符
取 600，留 4 倍余量
```

## 不能按固定字数切

最省事的切法是「每 600 字切一刀」——**这是错的**：

```
原来：  ...模型会先输出 一个「我要调用工具」的动
切出来：                          ↑ 一句话被劈开

正确：  ...我会先看 src 目录。然后跑测试。
                                  ↑ 在句号处切
```

做法是**递归**：先在最强的边界切，切不开再降级。

```python
SEPARATORS = ("\n\n", "\n", "。", "！", "？", "；", "，", " ")
#            段落     行     句号  感叹   问号   分号   逗号  空格
```

一段文字先用 `\n\n` 分成段落；某段还是太长，就用 `\n` 分行；
再长就用 `。` 分句……一路降级，最后才硬切。
**这就是 LangChain 的 `RecursiveCharacterTextSplitter` 干的事**，
我们手写一遍，因为它只有 30 行。

切碎之后必然有很多小片，再**合并**回接近 600：

```
【甲】200 字 + 【乙】180 字 + 【丙】190 字 = 570 ← 合成一片
                            + 【丁】200 字 = 770 > 600 → 丁另起一片
```

## 重叠：避免答案落在切口上

相邻两片要有 80 字符的**重叠**，否则答案正好跨在切口上时，
两片都不完整：

```
不带重叠：
  片1: ...A 公司 2023 年营收是
  片2: 12 亿，同比增长 8%。      ← 主语丢了

带重叠：
  片1: ...A 公司 2023 年营收是
  片2: A 公司 2023 年营收是 12 亿，同比增长 8%。   ← 完整
```

代价是存储和 embedding 调用都多约 15%，值。

**这里踩了一个坑**：最初按「剩余空间」算尾巴长度。一片已经
145/150 字符时，只剩 5 个字符的空间——重叠名存实亡。
正确做法是**给重叠预留空间**：正文按 `max_chars - overlap` 切，
重叠永远是完整的 80 字符。（`chunk_size` / `chunk_overlap`
这对参数在 LangChain 里就是这个含义。）

## 代码地图

一个文件，404 行，零新依赖：`apps/backend/app/rag/chunk.py`

```
split_markdown(text, source="a.md")
  ├─ split_sections()        按 # 标题切，标题路径带父级
  ├─ split_blocks()          分出「代码块」和「普通文本」
  ├─ split_by_separators()   文本递归切（段落→行→句号→…→硬切）
  ├─ _split_code_block()     超长代码块按行切，并补围栏
  ├─ merge_pieces()          拼回接近上限 + 带重叠
  └─ merge_tiny()            过短的并进相邻片
```

产物是一个数据类，四个字段都在为检索服务：

```python
@dataclass
class Chunk:
    source: str      # "step-07.md"      —— 命中后要能说清出处
    heading: str     # "上下文裁剪 > 为什么不做摘要"
    content: str     # 正文
    index: int       # 本篇内第几片
```

`heading` 带父级是刻意的：单独检索到「为什么不做摘要」时，
得知道它属于「上下文裁剪」，否则这片文档在库里是孤儿。

## 三个真实的坑

### ① 代码块里的 `#` 被当成标题

```bash
# 启动后端
uv run uvicorn app.main:app
```

`# 启动后端` 完全符合 markdown 标题语法。于是这个 bash 代码块
被判成两个章节，从中间劈开——两段都没有配对围栏。

`docs/step-01.md` 的「五、验收」就是这种情况：
那一节的围栏总数只有 **1 个**，源文档被切开时就已经坏了。

**修法**：先判围栏，再判标题。进了代码块就忽略 `#`。

### ② 超长代码块硬切后没有围栏

13 篇文档里有 **8 个**代码块超过 600 字符，最大 4458 字符。
直接硬切会得到：

```
片1: ```python
     a = 1          ← 有开头，没结尾
片2:  b = 2
     ```            ← 有内容，没开头
```

两片都是非法 markdown。**修法**：按行切，每片自带完整围栏：

```
片1: ```python  a = 1  ```
片2: ```python  b = 2  ```
```

这不是我发明的，所有正经的代码切分器都这么做——
「每片必须能独立被理解」是切分的第一原则。

### ③ 重叠把结束围栏复制到下一片

上一片以「结束围栏」结尾时，80 字符的尾巴里就含它。
复制到下一片开头后：

```
片1: ...代码...
     ```          ← 正常
片2: ```          ← 凭空多出来的孤立围栏
     ...代码...
```

**修法**：尾巴里含围栏就放弃重叠。重叠的目的是接上**文字**上下文，
一段代码的结尾没有这个价值，放弃它零损失。

## 验证

```bash
cd apps/backend
uv run pytest tests/test_s12_chunk.py -q     # 14 个测试
uv run pytest -q                             # 全量 148 passed
```

14 个测试里，有 4 条是为「防止重新踩坑」写的回归测试。
**但测试写了不等于有效**——所以做了变异测试：
故意把每个 bug 重新注入代码，看测试能不能抓住。

| 注入的 bug | 抓住它的测试 |
|---|---|
| 代码块内 `#` 当标题 | `test_heading_inside_code_block_is_not_a_heading` |
| 超长代码块交给普通切分 | `test_oversized_code_block_keeps_fences_balanced` |
| 重叠不检查围栏 | `test_no_dangling_fence_across_overlap` |
| 不给重叠预留空间 | `test_overlap_does_not_overflow` |

**这一步的变异测试抓出一个「假测试」**：
`test_overlap_does_not_overflow` 第一版造的样本每段只有 70 字符，
`70 + 80 = 150` 仍在上限内，注入 bug 也照样通过——**测了等于没测**。
改成 176 字符（贴着上限）才真正触发。

## 已知没做

- **42 个片段短于 100 字符**（多是「同上」这类导语），
  目前只是并进相邻片，没有更好的处理
- **表格没有特殊保护**（`| a | b |`），超长表格仍会被切开
- 切分**不感知代码语义**（不会因为是一个完整函数就不切）

这三条都不影响跑通，先记下来。
