# 第七步：上下文裁剪（L1 滑动窗口）

S6 的第一半（S6-1）只做了"度量"。这一步真的动手：**把发出去的历史压进预算**。

## 要解决的是什么

现在每次请求都把**全部历史**发给模型：

```python
history = await messages_for_llm(db, session_id)   # 一条不落
convo = [*history, {"role": "user", "content": body.question}]
```

而且工具落库之后，历史里还带着**每条工具输出**（一条可能几千字符）。

到某天超过模型窗口上限，接口返回 400。

**最糟的不是这次失败，是这个会话永久废掉**：超长历史存在库里，
下次打开还发一遍，还 400。用户只能删掉会话。

## 为什么不做摘要

L2（把老对话压缩成一段摘要）听起来更聪明，但：

- 要**额外调一次模型**（多花钱、多一个故障点）
- 摘要会把"具体执行了什么命令"揉成模糊描述

确定性裁剪粗暴，但**行为可预测**——作为第一道护栏更合适。

## 三条不可让步的规则

```python
# 1. 系统提示词必须留着
#    没了它，模型不知道有哪些工具
# 2. 第一条用户消息必须留着
#    那是原始任务，丢了一切都没意义
# 3. assistant 的 tool_calls 和配对的 tool 消息不能拆开
#    拆了上游直接 400 —— 比超窗更糟
```

第 3 条最要命。超窗至少能改预算，**配对拆了是数据合法性问题**。

## 核心思路：从最新往回装

```
预算 16000 token

  [system]                     ← 固定保留
  [user] 第一条                ← 固定保留
  ─────────────────────────
  [assistant] 老对话           
  [tool] ...                   ← 装不下了，从这里往前全丢
  ─────────────────────────
  [assistant] 上一轮
  [tool] ...
  [assistant] 最新回答          ← 保留
```

最近几轮才是模型当前在干的事，所以从**尾部**往前装。

## 关键设计：不可分割的单元

```python
def split_units(messages):
    """把消息切成"要么全留、要么全丢"的块。"""
```

绝大多数消息自己就是一个单元，唯独这两条必须绑一起：

```python
{"role": "assistant", "content": "", "tool_calls": [{"id": "call_1", ...}]}
{"role": "tool", "tool_call_id": "call_1", "content": "命令输出..."}
```

**为什么要单独做这一步**：如果按"一条一条"从尾部往前数，
边界很容易落在两者之间——留下结果、丢了声明，就产生孤儿。

## 踩的坑：测试差点没抓住 bug

我先写了 15 个测试全绿，然后做**变异测试**——故意把配对逻辑删掉，
看测试会不会红。

结果只有 3 个红，新增的那个"大小失衡"用例**照样绿**。

查了才知道原因：

```
每轮工具输出 20000 字符
→ 声明很小（几十字符），结果很大（上万字符）
→ 从尾部往回装：结果装下了，声明也装得下（它才几十字符）
→ 边界根本没机会落在两者之间，纯属运气
```

**真正危险的是反过来的情形**：

```
模型调 write_file
→ arguments 里是一整个文件（几万字符，声明巨大）
→ 结果只有一句"写入成功"（极小）
→ 从尾部：结果装下了，声明装不下 → 边界正好把一对拆开
```

补上这个用例后，再注入同样的 bug：

```
4 failed  ← 这次抓住了，包括新加的那个
```

**教训**：测试绿不代表测试有用。**故意把实现改坏，看测试是否会红**，
才知道它到底守着什么。

## 每轮都裁，不是只在入口裁

```python
while rounds < MAX_ROUNDS:
    # 关键：在循环内部，每次调模型之前
    convo, dropped = trim_to_budget(convo, settings.context_budget)

    async for delta in stream_deltas(convo):
        ...
```

只在入口裁一次的话：

```
入口裁到 16000
→ 第 2 轮调 2 次工具，历史涨到 22000
→ 又超了
```

因为工具输出是**在循环内部**不断累积的。

## 估算函数重新加回来了

上次（S6-1）我写了个估算函数，因为**没人调用**被删掉了。

这次它一写就有调用方——就是裁剪逻辑本身。这就是"什么时候该写"的答案：
**有真实调用方的时候写，代码和用途一起出现。**

系数 0.6 是量出来的：570 汉字实测 330 token（1 token ≈ 1.73 汉字），
取 0.6 故意往高估——宁可少装，不可撑爆。

## 结果可见（只在开发环境）

裁剪是**有代价**的：模型会忘掉早期细节。如果它悄悄发生，
你会遇到"明明说过的事它怎么忘了"这种玄学问题。

所以在 `done` 事件里加了 `trimmed`：

```
生产环境：什么都不显示
开发环境：finish=stop · 1 轮 · 5.2s · 8200 token · 裁掉 12 条历史
```

## 验证：用真实数据，不是造的

库里会话 #69 是最长的一个（52 条消息，含 13 组工具调用）：

```
消息条数: 52 → 28（丢 24 条）
估算 token: 28669 → 15814
系统提示词还在: True
第一条用户消息: 我是来测试 messages的
工具配对完整: True（声明 13 / 结果 13）
```

**这一步最重要的验收不是"测试绿了"，而是"拿真实会崩的数据跑一遍，它不崩了"。**

## 预算为什么是 16000

不是"窗口大小乘个比例"：

1. 网关没告诉我们窗口多大（`/models` 不返回 `context_length`）
2. 实测普通问答 ≈ 1400 token 入、带工具 ≈ 3100
3. 16k 约能装 5-10 轮带工具的对话，够用且便宜

要改就改 `.env` 里的 `CONTEXT_BUDGET`，不用动代码。

## 还没做的

- **L0 工具输出治理**：单条工具输出的上限（现在只留前 4000 字符，
  把末尾的报错切掉了）。它决定了 L1 多久触发一次。
- **L2 摘要**：暂时不需要。
